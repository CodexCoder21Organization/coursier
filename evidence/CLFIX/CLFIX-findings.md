INFERRED (fix choice): stop deleting the lock file by name. Rejected the alternative "verify after acquiring that the held channel is still the file at the path": Java has no API to read the identity (inode) of an open FileChannel, and verifying by opening the path again would open a second descriptor to the same file, whose close drops the process's POSIX (fcntl) locks on Linux and macOS (the FileLock javadoc warns about this). Not deleting is correct on both because every contender then always locks the one file the path names. Cost: an empty `<name>.lock` stays beside each downloaded file/archive directory. Not covered: a process running an older coursier that still deletes after release can still break ownership for others sharing the cache; CachePath.withStructureLockOnce still deletes `.structure.lock` after release (same pattern, not exercised, not changed).
