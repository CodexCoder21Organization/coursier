INFERRED — The author's JVM rationale is sound for a portable implementation using the public Java APIs. FileChannel exposes neither a descriptor nor file-identity attributes. Reading fileKey through a Path identifies the current pathname, not the file held by the existing channel; reading before and after open does not close the intervening replacement race. ### 2. Structure coordination: reachable ordering, no wrong Maven result found

OBSERVED — Read [CachePath.java](https://github.com/CodexCoder21Organization/coursier/blob/f11bef695a648b6cf43fc90969e72887411f2f96/modules/paths/src/main/java/coursier/paths/CachePath.java) in full. The File overload opens `.structure.lock`, blocks on its channel, invokes the callback, releases/closes, then deletes by name. A queued B can acquire the old inode after A releases it; A then deletes its name; C opens a new inode and acquires it while B is still in its callback. This ordering is reachable here too.

OBSERVED — The Path overload is different: it opens with DELETE_ON_CLOSE. OpenJDK's UnixChannelFactory unlinks that pathname immediately on open, before the caller's channel.lock, so independent processes can obtain different inodes even without waiting for a previous release. No production call site in this fork directly uses that Path overload except the corresponding forwarding overload. Source: [OpenJDK UnixChannelFactory](https://github.com/openjdk/jdk21u/blob/master/src/java.base/unix/classes/sun/nio/fs/UnixChannelFactory.java#L253).

INFERRED — This does not undo the fixed download lock. CacheLocks' structure callback creates parent directories and opens the per-file coordination file; concurrent CREATE opens converge on that same existing inode now that it is not deleted. Downloader's other structure callbacks create parents, open the temporary output, atomically rename it, or delete it on failure, all within that artifact's still-held per-file ownership. Concurrent mkdir for a shared parent is idempotent; `Util.createDirectories` also handles an already-existing directory. Distinct artifact owners operate on distinct temporary/final names. The structure lock is not the only protection of either download stream. What a Maven build sees through this ordering is successful directory creation and its normal complete result, not two owners of its `.part` file.

INFERRED — **Structure-lock repair can follow.** It is a real coordination defect worth a public-API three-process test, including both overloads, but I found no route through the production Maven callers where this ordering yields a wrong or incomplete returned result. That is the brief's condition for blocking on this separate defect. The public callback helper itself should not be described as reliably exclusive across processes today.
